## Open items that are not yet decisions

- **Queue timing for the 24-GPU judging point:** needs 6 idle GPU nodes; pick a quiet window and check `sinfo` beforehand.
- **Startup measurement rule:** first Qwen3-8B load took 366 s (215 s was a first-time download, 142 s NFS read). Decide whether to report cold or warm cache, and pre-stage weights before timed runs.
- **Strong-scaling workload sizes:** fixed by pilot runs (1-GPU baselines must finish in practical time).
- **Training cost (first measurement, 2026-11-24):** 0.93 examples/s on 1 V100 (16-example run, rough), so about 72 min of processing for 4,000 examples at 1 epoch. Worker startup was 351 s (model load and 4-bit quantization from the shared filesystem) and driver startup (Ray cluster start plus worker launch) 54 s. Confirm at larger sizes; decide the cold vs warm cache reporting rule.
- **Smoke runs 2026-11-24 (1, 2, 8 GPUs; Ray multi-node works):** worker startup 351 s (1 GPU, first run), 186 s (2 GPUs) and 195 s (8 GPUs, concurrent with the 2-GPU job); driver startup 54, 58, 70 s. Startup varies about 2x between runs, so cold vs warm cache needs repeats and a reporting rule. 8-GPU smoke run was a single optimizer step, so its processing time says nothing about scaling.

- **Ray cluster startup:** one Ray head on the first node and one worker per other node, started inside the SLURM job via `srun` + `apptainer exec --nv`, before the driver connects. Per-job unique ports.
- **Ray dashboard:** with the dashboard ON (own port per job) the `Failed to query Ray Train Controller actor state` lines still repeat, so the dashboard flag is not their cause. They are harmless log noise; filter when reading logs. Dashboard stays on; check whether timeline data is obtainable.

## Cluster notes (working knowledge, not decisions)

- **Two-node NCCL (checked 2026-11-22):** inside the container, NCCL 2.20.5 uses InfiniBand (`NET/IB`, mlx5_0) between nodes; no TCP fallback. Measured 3.93 GB/s bus bandwidth for a 256 MB fp32 all-reduce on 2 nodes x 1 GPU (`experiments/nccl_check.py`). GPU Direct RDMA is disabled on Wahab, so GPU traffic is staged through host memory. The `ibv_set_ece` warnings are harmless.

- Wahab's login shell is csh/tcsh. Run `bash` first for `export` and `VAR=value` syntax.
- Heavy jobs (for example converting a container image) must run as batch jobs on compute nodes, not on a login node.
- `!` typed at an interactive prompt can trigger history expansion; prefer `sbatch --wrap` or the file editor over heredocs containing `#!`.
- **vLLM in the container (checked 2026-11-25):** the serving environment's vLLM needs the CUDA 13 runtime, which is not on the library path by default; `slurm/in_serve_env.sh` adds `site-packages/nvidia/cu13/lib` to `LD_LIBRARY_PATH` (driver 580, CUDA 13.0). vLLM runs on V100 through the Triton attention backend (FlashAttention 2 needs compute capability 8). Harmless warnings: numba fails to import (NumPy 2.5), and the adapter directory has no model `config.json`.
- **vLLM startup anatomy (one 2-GPU replica, 326 s to ready):** container + imports about 45 s; weights 8 s; `torch.compile` 38 s (cached under `~/.cache/vllm`, so later servers reuse it); CUDA graph capture about 70 s on each GPU; engine init total 192 s. First-run vs later-run startup will differ because of the compile cache, like the cold/warm effect in D29.
- **Serving startup, same node, same job:** server with warm caches 160 s to ready (weights 8 s, compile cache hit, engine init 51 s); the merged model, read for the first time from the shared filesystem, 326 s (weights 139 s, new compile 25 s, engine init 95 s). Cold weight reads and a missing compile cache can double serving startup, as with D29. The merged model needs reading once per node.
